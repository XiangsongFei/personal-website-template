# S3.4 权限矩阵与隔离库业务测试申请草案

范围为 M1–M4 与 R3 增量候选。**以下所有业务正例、跨租户行级负例及预算均为计划，真实执行状态为 NOT RUN。** 已取得的历史验收只覆盖当时的环境。本矩阵引用源码、历史收据及本批的独立 READ ONLY/ROLLBACK 收据。没有读取 JWT、改动用户或发送业务测试请求。

## 测试身份与现有边界

- 隔离项目 `ecv-s33a-20261109-7dd22a81`。历史 Alice UID 为 `a33b0000-0000-4000-8000-000000000001`；沿用旧计划预留的 Bob（末段 `000000000002`）、Charlie（末段 `000000000003`）及各自的 `s33b-runtime-<name>-20261109@example.test`。Bob 的站点记为 B，Charlie 为普通无站的对照。任何身份或邮箱冲突都立即停止，沿用历史虚构数据时仍须按 UID 隔离。
- 上一批 Alice 的普通密码登录、当前用户、Session、Refresh Token、password AMR 绑定已真实通过；三个私有 Profile 均收到 406/PGRST106。C01 和六请求两个历史窗口均已独立核实零邮件。上次批次已消费，执行器结束时没有供本批复用的密码、JWT 或登录回执。即使旧 Session 行尚在，签发 issue 仍要求本次服务端实际观察到的普通密码登录，而后重新验证 issuer、audience、UID、SID、AMR、用户可用性和 Auth Session；仅凭 Cookie 或旧收据拒绝。保留历史 CLI 422 字节 stderr 的 UNKNOWN。
- M3 的 `auth_source_identity()` 位于 `site_private`，由 postgres 持有，固定空 search_path。调用者首先须满足由真实 PostgREST 签名验证建立的 authenticator/角色上下文；普通角色没有直接执行权。`ecv_s3_authz_reader` 承担内部调用。资格以当前 UID/SID、Grant、epoch、hold 与时限为准。M4 将站点权威 Owner 和有效 Owner 镜像纳入读取与事务约束。
- 五个现有用户入口是 `site_api.apply_business_grant(jsonb)`、`create_site(jsonb)`、`get_my_site()`、`read_create_operation(jsonb)`、`read_introduction(uuid)`。第一个属于 grant_writer，其余四个属于 command_writer；均为 SECURITY DEFINER、空 search_path。普通角色中仅 authenticated 有这些 EXECUTE，内部角色均不登录、无 BYPASSRLS。对照完整表/列 ACL、Owner、RLS、函数体和成员记录检查所有实际增量。
- **正例传输是独立门禁。** M4 仓储使用 `Content-Profile: site_api` 并经本地 PostgREST 转发；既有网关仅暴露 public。应先独立审核一个保留真实 JWT 验证、只允许五个用户操作的项目私有调用路径，检验其网络可达面、调用角色与 Auth 桥接语义。此计划对新增公开包装器、修改 Data API schema、直连数据库伪造 GUC、使用 service_role 代用户的预算均为 0。这一私有用户路径仍未配置。另据本批固定 PostgreSQL 17.11 的独立 READ ONLY/ROLLBACK 实测，`current_setting('ssl') = off`。登记通道要求经专用 CA 与目标 SAN 校验的 TLS，当前不能安全建立。B–G 真实业务闭环均 BLOCKED，严禁降级明文、跳过主机校验或自动修改 PostgreSQL。

## A–G 分阶段预算

以下是未来上限，用于编制逐次审批文件。各阶段先复核新鲜目录和数据基线，记录单次批准消耗。按服务边界计数：一次内部业务 RPC 至多一个指定 PostgREST 请求；调用本地候选 Worker 接口时另计一个入口请求。每次需要新验身份时 `getClaims`/JWKS 至多一个网络请求，`getUser` 至多一个。故单个业务用例上限为 4 次 HTTP（Worker 入口、Claims、User、一个 RPC）；不允许 SDK 隐式刷新、探测、重定向或重试。受控登记通道按独立数据库语句另计，一张票据至多登记一次。不使用 HTTP 代替登记通道。每个普通密码登录另计最多 4 次 HTTP（入口、密码登录、Claims、User）和最多 4 条 Auth 新行（login 审计、Session、Refresh Token、password AMR 各 1）。若最终适配器有不同层数，必须先缩小到已冻结路线或另审预算。只读目录核验独立 READ ONLY/ROLLBACK，不调用任何带写/锁行为的业务 RPC。

**合计与前置预算**

1. 站点行按 M4 的实际 SQL 计算：sites、site_members、site_domains、site_settings、section_state、site_publications、intro_entries、draft_revisions、operation_requests、site_audit_events 各 1，site_locales 和 intro_translations 各 2。合计每站 12 表 14 行，两站最多 28 行。逐站核对 `sites.owner_auth_user_id`、唯一 active Owner 镜像、同站 parent/FK、语言 zh/en、唯一回执/审计及未发布约束。站点、条目、回执等服务端 ID 只在独立确认提交后绑定到操作 ID。没有真实 DNS、快照、发布写入或外部域名注册。
2. 基本方案 Grant 最多 4 行（Charlie 两个 SID，Alice/Bob 各一）、资格状态最多 3 行、消费回执最多 6 行、登记最多 7 行，另有 Charlie S1 Grant 两次 UPDATE。为每次预期成功或失败的登记封存独立 proof_id 与时限；密码/密钥/签名原文不进计划。采用新 CLI 部署、受保护主体登录配置、私有测试入口、开发测试密钥注入、单条 kid 注册、资格状态初始化以及开关开启/关闭均须另列操作和授权。初始化角色不得将未知 hold 当作明确解除。
3. Auth 计划上限为两个新账号（Bob、Charlie），各一次受控管理创建（HTTP 各1，用户、Identity、创建审计各1）；Alice 创建 0。四次独立、正常密码登录（Alice 1、Bob 1、Charlie 2，HTTP ≤16），新增登录审计/Session/Refresh Token/AMR 各 ≤4。合计新增 Auth 行 ≤22；不自动退出、刷新、清理或发送邮件。旧 Alice 密码未持久化，如没有获批的新登录凭据，D 为 BLOCKED。若单独批准一次 password-only 管理更新，还需另加管理 PUT 1、更新审计 1，且会使 Alice 所有既有 Session 失效并影响其关联记录。先按当前目录与只读行数冻结 Session、Refresh Token、AMR、one-time token 的逐表删除/吊销预算，再决定是否允许改变旧 Session；默认这些差异的额度为 0。不得套用历史零 Session 时的改密预算。
4. 所有预期拒绝需冻结具体层、HTTP/SQLSTATE 及允许的结果形状。持权/持票据的正常路径需要分别有正例，拒绝结果需与独立只读前后状态吻合。任何意外成功、数据泄漏、超预算、身份漂移、超时或未知提交立即 STOP，记录已发出请求并保留凭据消费状态；没有自动重试/清理/补发或补写历史。
5. **有条件的真实竞态与 UNKNOWN**。D/E 完成后 Alice/Bob 都已有站，继续抢同一新域名只能遇到 Owner 唯一约束。要验收“两个原本无站账户抢同一域名”，另批一个干净来源和两个获准、有资格且无站的账号，或单独设计替代 D/E 的两连接首次建站。独立替代场景上限为已预签的两个 HTTP 建站调用（业务链 ≤8 HTTP）、两个数据库事务、一个成功站点/14 行；不在原环境追加新账号或第三个站。需要新的账号、资格、登录、额外站点或故障代理时必须另行逐项审批。真实 UNKNOWN 优先封存两侧时间线及后验；从原键只读恢复保留为单独的一次操作。没有真实竞争、预定故障或受控交错证据时，该项保持 NOT RUN/UNKNOWN。
6. 预留 Alice/Bob 的 UID、邮箱、`alice_create`、`bob_create` 和其他请求名来自既有 `runtime/plan.json`（SHA-256 `51eca6eaba70c6027fc1aff70fc7a59956788edc7ec43d3d595450f6b8253abe`）。其中历史 `RESERVED_NOT_CREATED` 已被 Alice 的创建收据更新。真实审批前须冻结请求用途与 ID/slug/摘要的新映射、主体和 kid、数据碰撞检查、调用路径、端口及项目绑定；不要重新使用旧的已消费授权。

## R3 专项实测附表

下表为 B/C 的可替代故障用例。真实执行均 NOT RUN；表内超出基本方案的登记、密钥状态更新与运维操作必须单列预算，不能从失败场景挪用剩余额度。签名、密码和 JWT 全程不落盘。审计只记录调用层、身份匹配布尔、作用域内操作 ID、实际事务结果和行数。

| 用例 | 编排与验收 | 单用例新增写入上限 |
|---|---|---|
| 验签拒绝 | 预先封存的错误 MAC、错误 kid、错误用途各一次；Worker 明确拒绝，验证登记及消费均未发生。不得把合成数据识别当作真实签名 PASS。 | 每个用例 ≤1 Worker 请求和 ≤2 身份复核 HTTP；登记/回执/Grant 均 0。 |
| 已登记票据的绑定拒绝 | 对同一合法登记分别以错误 UID、SID、project/action、digest 及真实超时消费；不修改服务时钟、JWT 或数据库目录。要隔离 SID/UID 条件，使用已独立认证的另一固定会话。 | 一条登记；每个拒绝尝试最多一个业务调用（≤4 HTTP）；成功消费和 Grant 变更 0。 |

| 撤销与续期并发 | 同一活跃 Session 两张目的不同的票据、两个真实后端 PID；不论哪次先获锁，最终资格须撤销。续期可在撤销前先成功，撤销先提交则后续续期必须拒绝。 | ≤2 登记、≤2 消费调用、≤2 回执、同一 Grant 最多 2 次 UPDATE，无 Grant INSERT。 |
| 原子性与不确定结果 | 在另行批准且能隔离的真实 JWT 事务测试入口，验证一个已执行写入的事务在提交前回滚后，Grant/消费回执一起消失；先行独立提交的登记仍应保留。真实入口无法控制事务终止时标 NOT RUN。丢失响应使用原 proof_id / request_id 关联只读目录验收，成功、未观察、未知三类独立报告。 | ≤1 登记、≤1 消费调用、≤1 故障注入，已明确回滚时新 Grant/回执 0；若这是单独批准的未知提交用例，只允许原操作的合法最大影响（至多 1 回执及 1 Grant 变更），额外登记/签发/重发 0。 |

**事务及轮换合同。** 真实消费事务须为 READ COMMITTED，先取全局配置事务级共享 advisory 锁，再锁用户安全状态行，锁后复核身份、时限及 epoch，随后锁同一用户/Session 的 Grant 行（若存在），更新 Grant、写唯一消费回执，同一事务提交。登记事务取同一全局共享锁并追加票据，不锁业务 Grant。配置变更取全局排他锁。续期必须使用首次 issue 记录的同一 kid，且其签发与验签时窗仍合法；轮换后用新 kid 给旧 Grant 续期应拒绝 `42501`，不延长原 Grant。可独立批准另一代元数据最多 1 行、一次跨代续期登记和一次消费调用、合法回执与 Grant 变更 0；不得再次签发来掩盖错误。撤销旧 kid 后该代 Grant 的业务资格立即失效，保留原登记及回执。

回执查询本身 `read_create_operation` 也会经 M3 的 `lock_business_qualification` 锁住安全状态行。它是具有真实 JWT 的受控业务请求；独立 READ ONLY 审计应只查询系统目录与已批准的状态聚合，不能在 READ ONLY 中模拟该 RPC。

## 准入与停止点

最小下一批为 A 单次迁移及独立目录验收，其余批次请求、密钥和账号额度均为 0。前提是 R3 候选审核、摘要及 PostgreSQL 17 非超级用户权限前检满足书面审批。M5 继续保留 M3 的 `CHECK (NOT proof_verifier_ready)`，并加入 `CHECK (enabled = proof_verifier_ready)`。A 成功仍不允许开启任一开关。B 前必须单独审核并批准解锁 DDL、认证 TLS 通道及受限 JWT 传输，其后才可分别请求 B–G 的具体动作。私有业务传输、可审查的凭据生命周期、明确无 hold 的合法授权来源、最新会话或必要的合成身份缺任一项，相应正例保持 BLOCKED。跨租户编辑/删除业务 API、Storage、发布和公开快照读取进入各自功能阶段验收，预算均为 0。
