# S3.3 R3 可信证明候选

本轮变更针对固定开发基线 e449c25faf26c77bedd9a8cf09850b96eea3e9a3。已部署的 M1–M4 原文件和 S3.2 历史合同完整保留。M5 只生成候选文件。本地 HTTP 隔离和零邮件验收仍成立。本轮没有再次调用 Auth 或业务 API。

## 密码学决定与合同差异

M3 的 verify_business_proof 调用 pgcrypto.hmac 得到 32 字节，再用 PL/pgSQL 固定 32 轮 XOR 比较。数据库已用 CHECK 强制关闭该分支。固定轮数没有给解释器、内存访问和比较过程提供恒时保证。固定库先前的扩展成员目录只验证了 pgcrypto 1.3 和 Vault 等实际函数。PG17 hmac 只计算 MAC，原生 bytea 相等比较亦没有合格的密码学比较合同。[PostgreSQL 17 pgcrypto](https://www.postgresql.org/docs/17/pgcrypto.html)

|方向|信任与部署|本次决定|
|---|---|---|
|A，数据库原生验签|一个由供应商支持的原生 HMAC-SHA-256 验证函数可保留原有数据库独立验签合同。需要目标实例上的实际 SQL 接口、维护与构建证据、最小 EXECUTE 权及非超级用户可用性。当前没有这样的已验证接口。|不安装扩展，不假设 pgsodium 可用，也不使用普通 SQL 比较。|
|B，Worker 验签并登记|Worker 只在固定项目、可信账号句柄和签名合同均成立时向专用 PostgreSQL 主体登记。数据库接受源自该主体的封存字段，再用其自己的 Auth 桥接、RLS 和状态行检查兑换。新增了一个能够证明“验签已完成”的服务身份。|采用关闭态候选。相比供应自定义 C 扩展，数据库部分只用现有 PG17 能力，并保留 M4 的五个既有用户入口及 Data API 边界。|

原 S3.2 第 4 条要求**数据库校验签名**。方案 B 在 Worker 验签，数据库验证独立登记事实。签名的 v1 字节保持兼容，数据库兑换报文改为仅含 proof 的对象。DB 拒绝旧 signature 报文及 verified=true。新合同须在任何正例启用前单独确认；若必须由数据库独立持有并验证 MAC，则此候选保持关闭，转回方案 A。批准当前离线开发不能替代该决定。

13 个平面标量按 proofFields 固定顺序、UTF-8、LF 与 ecv.proof.v1 域编码。payload_digest 绑定 ecv.business_grant.v1、action、purpose、uid、session_id、epoch，签名再覆盖项目、proof_id、kid、时间及事件。Worker 对输入快照和固定 64 位小写十六进制格式进行检查，以 WebCrypto HMAC/SHA-256 计算期望值，用 node:crypto.timingSafeEqual 比较两份 32 字节数组。固定 workerd v1.20261023.1 将此 API 委托给原生实现，后者调用 CRYPTO_memcmp。恒时主张只覆盖同长度 MAC 的比较；语法错误、密钥查找、数据库往返和整条 HTTP 请求的用时仍可不同。[固定 workerd 的 Node API](https://github.com/cloudflare/workerd/blob/v1.20261023.1/src/node/crypto.ts#L9-L14) · [固定原生实现](https://github.com/cloudflare/workerd/blob/v1.20261023.1/src/workerd/api/crypto/crypto.c%2B%2B#L1210-L1217) · [Node 的保证与限制](https://nodejs.org/api/crypto.html#cryptotimingsafeequala-b)

新表 proof_generations 只保存非秘密 kid、签发/验证时间窗和单向撤销时间；registered_business_tickets 保存 proof_id、受限 UID/SID、kid 和已验的声明。两表属 ecv_s3_owner，均 FORCE RLS。grant_writer 对票据有 INSERT、SELECT，对代次有 SELECT；authz_reader 只读代次。票据 INSERT 只能出现在受控登记身份的调用下，票据读取按当前请求 UID 限制。无普通角色新授权。注册角色仍可能有 PostgreSQL 集群的公共基础权限，正式启用前应按真实平台检查数据库 CONNECT/TEMP、受保护 schema 及可达 SECURITY DEFINER，而非假定 NOINHERIT 会屏蔽 PUBLIC。

登记身份本身是一条新授权通道。取得它的人可冒充验证服务登记声明。其单独泄露仍不能赋予其他用户 JWT，却足以破坏对应身份的业务签发信任。执行身份、TLS 对端、证书、签名材料、私有调用路径及轮换必须分别约束。不能把浏览器提交的签名、验证布尔值、Cookie、actor 参数或 GUC 当作此通道。

## 原子性、撤销与 UNKNOWN

- 登记和消费是两个独立事务。登记在 INSERT 可能等待唯一索引之后再次检查时限。登记重复返回 PT409，无游标通道。消费只允许 READ COMMITTED，以共享配置事务锁（3303,5）、用户安全状态行、Grant 行及消费回执的顺序操作。配置/代次变更取同一排他锁。维护任务不能以相反顺序同时改代次和用户状态。
- 消费在取得用户锁后重新判断 Auth 身份和时间。只有已登记的精确声明能够进入 Grant 分支，已消费 ID 返回 42501。回执的全局主键是最终唯一性保护。写回执后复核到期时间，错误让当前事务全部回滚；此前单独提交的登记可以保留。登记发生不确定、消费响应丢失或事务未观察到时按原 proof_id 在受控运维通道只读核对，禁止重新签发新 ID、重发、清理或宣称回滚。
- 资格有效期滑动 30 分钟，绝对 12 小时，Proof 最多 60 秒。续期不能复活已过期、已撤销、跨 epoch 或跨 SID 的 Grant。续期须使用初次签发的 kid。只要当前代次明确撤销，该代次签发的 Grant 的后续业务资格立即拒绝（在配置锁先后次序内）。正常轮换应为旧 Grant 留足续签窗口，或要求新鲜密码登录和新 SID。另用合格在用代次签署定向 revoke。禁止复用旧 kid 或反撤销。
- 真实 Auth 管理操作和业务数据库不是一个事务。业务锁不锁定 Supabase 管理的 Session 行。S2 改密、退出和 Recovery 在引入业务资格时应先提交受控 epoch/hold/撤销，再进行 Auth 生命周期操作；外部管理员操作及最后一次检查至提交的间隔须另验。不能从短 TTL 推导跨系统强原子性。

## 密钥、传输与回撤

生产 signer、注册主体凭据和调用路径均未配置。后续隔离测试需单独批准一份环境/用途专用的 256 位随机 HMAC 密钥、独立 kid、项目专用私有 CA/证书及专用登记登录凭据。只从服务端密钥存储载入非导出的 HMAC CryptoKey；签发和验证各自解析经审核的 kid 及有效窗。对称算法意味着能计算期望 MAC 的验证服务同样具有造签能力。不得交给浏览器、旧 CMS、普通角色、日志、迁移或共享缓存。数据库的代次表只存元数据，不保存 MAC 密钥。

固定 PostgreSQL 17.11 的独立目录查询实际返回 ssl=off。直接登记候选固定 127.0.0.1:56322/postgres、专用登录、独立 CA 和对 IP SAN 的真实验证，禁止明文降级。驱动不能证明已验证对端时拒绝交出密码或登记。当前 Worker 的用户仓储请求 site_api Profile，而 Data API 只暴露 public。**两个真实传输门禁均未通过。** 云上 Worker 的 loopback 也不等于此 Mac。生产需单独审核固定托管项目、网络位置、角色、驱动及 TLS（或经过验证、固定身份、关闭登记查询缓存的专用 Hyperdrive）、私有 JWT 传输入口和真实 JWT 验证；不更改现有 S2 或公开私有 Schema。[Cloudflare PostgreSQL 客户端](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-drivers-and-libraries/node-postgres/) · [查询缓存说明](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/)

紧急泄露先阻断签发和登记通道，在授权维护事务中关闭双开关并撤销受影响代次，保留登记与消费历史；针对受影响用户冻结资格、递增 epoch、处理已发 Grant，再独立轮换登记凭据和检查既有连接。NOLOGIN 仅影响后续登录，活动连接要另行处理。两张新表的 FORCE RLS 没有给一般维护主体授予写策略。初始化资格状态、维护代次、关闭/重开等动作必须预检实际合法维护身份及对应预算。禁止用普通账号或新增 BYPASSRLS 绕过。M5 本身处于单一事务；部署失败要查明提交状态，成功后的回撤优先保持关闭，不回退到旧 PL/pgSQL MAC 比较。

## 后续审批顺序

1. **A 仅闭态安装**。先接受信任边界的候选差异，核验目标、M1–M4 摘要、19 个函数指纹、完整 ACL、五条既有 bootstrap 记录、原数据和运行时双关，再单次应用 M5。预计 19 表、143 列、23 函数、24 业务触发器、37 个策略、6 内部角色与 6 条精确 bootstrap ADMIN 记录。两张新表均空。五个原用户入口、原 17 表及业务内容继续保留。新角色 NOLOGIN、0 个凭据、0 用户/Session/HTTP、0 业务行。新的独立 READ ONLY 事务逐对象验收后 ROLLBACK。若直用 psql，记录 CLI 迁移历史差异，不补写。A 不要求把 PG TLS 打开。
2. **B 之前的独立前置审批**。分别冻结可行的 TLS 通道和服务身份、受保护的一次性操作记录、仅获准 JWT 业务请求的私有传输、合法的资格维护路径与测试密钥来源。启用登记需一次角色登录能力变更和专用授权，代次起步最多一条测试元数据行。开启门禁需要一次新的已审核前向变更移除旧硬关闭约束、保留双门一致，并由获准维护操作更新唯一 runtime 行。上述动作均不在 A 内。正常业务资格不能自动清除密码变更/恢复 hold。
3. **B–G** 每一项 freeze 真实端点、请求数、字段、标识、行数、故障处置和独立验收。详见 [Alice、Bob、Charlie 权限矩阵与预算](S3.4-AUTHORIZATION-TEST-MATRIX.md)。每个签发 intent 在受保护宿主中最多有一条预批准记录、一次不可恢复的消费；预算用尽、响应 UNKNOWN 或重复 ID 停止，不补发。历史 Alice 保留且重新验证 Session，不创造可复用的历史授权。

### 单次签发的持久记录

候选 R3IntentLedger 只提供内部 claimOnce。固定项目在受保护的 namespace 中使用唯一对象名；对象还核对自己的实际 ID。键为项目及 proof_id，值包含完整批准的七字段意图与有效期。storage.transaction 中只进行批准窗口和字段比较、把 approved 改为 consumed。事务内没有网络、取钥或签名，丢失确认时按原 ID 对账。生产请求不接收命名空间、审批内容、kid、epoch 或数据库客户端作为请求参数。该类未导出到实际 Worker 入口、未配置绑定、没有公开 fetch，以及创建、解除或重置审批的方法。测试中的事务存储为模型，真实持久性与跨 isolate 竞争需未来专项验收。[Durable Object 事务接口](https://developers.cloudflare.com/durable-objects/api/legacy-kv-storage-api/)

源计划与凭据必须分开。下批对一个 proof_id 最多预批准持久记录 1 条、消费状态更新 1 次；登记数据库票据 1 条，成功消费回执 1 条。注册事务回滚和数据库拒绝消费不能恢复持久签发机会。新普通登录的 SID 在服务端验证登录之前未知。审批应预先固定唯一主体、动作、kid、epoch、proof_id、总预算和“仅绑定该次正常登录的 SID”规则；由独立受保护的准备流程在验证后一次性落定精确 SID，再在新鲜登录回执有效期内签发。不能使用 SID 通配符、旧 Session 行或想象出来的回执。没有获准的精确预置来源时，真实签发继续关闭。后续部署需选择该项目独立的 namespace 与存储后端并验证真实配置及持久 CAS；本轮没有任何 Cloudflare 资源配置变更。
