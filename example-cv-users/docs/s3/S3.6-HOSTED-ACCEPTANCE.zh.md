# S3 托管验收候选

本地候选基于 PR #56 的 `f1d0ce3d5534c1a4764cdb74b94d89db0328e419`。当前状态为 `HOSTED_LOCAL_CANDIDATE / HOSTED_REAL_NOT_RUN`。旧 REF 保留其独立历史结论。托管项目的应用验收无需等待 `REF_R0_REAL_ACCEPTANCE_PASS`。

## 文件与兼容性

| 文件 | 托管路线 |
| --- | --- |
| M1 `supabase/migrations/20261107180504_s3_security_foundation.sql` | 业务安全状态、Session Grant、proof ledger、私有 schema 和强制 RLS 原样入包。安装依赖 PG17 非超级 `postgres`、角色创建能力、OID 10 的实际 grantor、临时 SET/INHERIT 边和 `auth.users(id)` REFERENCES。 |
| M2 `20261107180505_s3_site_foundation.sql` | 站点、Owner 成员关系、草稿、审计及永久 unpublished 行原样入包。延迟完整性触发器、角色所有权及 RLS/ACL 保持；依赖 M1 的角色边和 Auth FK。 |
| M3 `20261109104800_s3_business_grants.sql` | 原样作为闭态迁移入包，`auth_source_identity()` 需要 `postgres` 已有的七个 Auth 列读取权、schema USAGE 与 BYPASSRLS。需要 `extensions.hmac/digest` 和角色权限。冻结的本地 issuer/project 在后续闭态绑定文件替换。 |
| M4 `20261109104802_s3_create_site_commands.sql` | `create_site`、`get_my_site`、初稿与操作读回原样入包，依赖已验证 M3。初始化文案是固定合成夹具，revision 0 摘要仍采用旧 `jsonb::text` 域。 |
| M5 `20261110183047_s3_registered_business_proofs.sql` | 原样保留前置函数 hash、登记角色、proof generation/epoch、登记与消费锁、撤销和当前资格校验。闭态物理约束 `NOT proof_verifier_ready` 仍生效；启用需要独立、可审查的状态转换。 |
| M6 `20261111045534_s3_closed_service_roles.sql` | 原样保留两类 NOLOGIN、限额及有效角色边测试。托管 `postgres` 是否可按所需 grantor 委托 `authenticated` 是实际能力门。 |
| M7 `20261111045535_s3_private_service_identity.sql` | 先原样装入，再按既有定义的 hash 审核 issuer 替换。要求 `session_user=ecv_s3_internal_api_login` 和 `role=authenticated`；登记需要另一个专用登录。托管 Data API 使用 `authenticator`，故走独立本地 PostgREST、Unix socket 和现有 mTLS ingress。 |
| S3.6 `01-text-publication.sql` | 原样入包。保留在锁内的当前资格复核、CAS、请求指纹、原子 revision/receipt/audit、发布指针和 outbox。闭态前向补丁额外撤销普通用户 publish/unpublish EXECUTE，首批只允许打开草稿保存。01 的 `public` 函数所有权迁移需要部署者可委托对应 schema CREATE。 |
| S3.6 `02-text-outbox.sql` | 原件按 SHA 核对，首批不安装。以后另审其 worker 主体、私有应用入口、claim/lease 与暂停、UNKNOWN、真实投递边界。01 中的 outbox 行与发布本来在同一事务，首批要求零快照、零 outbox。 |
| `supabase/candidates/s36-a1/native-auth-acl.sql`、`native-auth-readonly.sql`、`supabase/candidates/s36-a2/initial-readonly.sql` | 自建初始化和证据。OID 10 登录、Unix socket、`pg_control_system` SID、Auth owner 重授、快照 ledger 和 GoTrue migrate 由原实验包负责。托管走平台原生 Auth，应用迁移不改 Auth ledger、owner、HBA 或平台角色。 |

受保护 Auth schema 的已有权限即实测输入。首选保持已冻结的内部窄函数与所有权限断言。不将缺失的 SELECT、REFERENCES、角色管理或 schema 权力换成广授权。新项目若在只读预检或原 SQL 检查失败，停止并只针对该项另审前向变更。既有 Users 的 `worker/index.ts`、生产配置、域名与部署入口均在本地测试入口之外。

## 本地入口与参数

从 `example-cv-users` 执行。现有历史原件在工作树 `s3-5-s3-6-assets-publish-20261113` 的 `example-cv-users/supabase/candidates/s36-text-only`。生成器逐件校验 M1–M7、01/02，输出顺序和摘要，并生成目标绑定、默认闭态的 `hosted-project-closed.sql`。它只写新本地目录。

```sh
node scripts/s36-hosted/stage.mjs "$APPROVED_TEST_REF" "$HISTORICAL_SQL_DIR" "$NEW_PRIVATE_OUTPUT_DIR"
```

现场安装前使用 `supabase/candidates/s36-hosted/preflight.sql`。固定目标直接连接 `db.<已审批项目 ref>.supabase.co:5432/postgres`，以目标专用 CA 校验 `sslmode=verify-full`。清理继承的 `PG*` 配置，凭据放在单独的 0600 文件。部署器使用 `psql -X -v ON_ERROR_STOP=1` 与已审 manifest 顺序逐文件执行，出现第一项错误即停。已有对象冲突、错误签名验证或权限不足后，检查已提交迁移及目录并对账，勿自动重跑。包的最后阶段仍是闭态。

本地 CLI 使用 Users 的 `createIdentityAdapter`、`createSiteService`、`createRpcRepository` 和私有入口。配置 JSON 必须 0600，字段为 `project`、`publishableKey`、`privateOrigin`（带端口的 `https://127.0.0.1`）、`alice`、`bob`（Auth UID）、`aliceSite`、`bobSite`、`entry`（Alice 默认简介条目 ID）、`requestId`、`expectedDraftRevision`（首轮固定 0）。拒绝 Users/CMS 生产项目、非 loopback 业务入口及 secret/service key。Auth URL 从项目 ref 构造，拒绝跨目标请求和重定向。

- 原生 PostgREST 可作为单独本机进程运行。只在 `/private/var/tmp/s36-hosted-<批次>/postgrest.sock` 监听，由运行用户控制的父目录 0770，socket 0660。只用 `site_api`，配置固定 `authenticated` audience、目标项目的公开 JWKS、专用 `ecv_s3_internal_api_login` 的连接材料及对实际数据库主机的 TLS 校验。托管 Data API 不增加 `site_api`、`site_data` 或 `site_private`。账号及 Auth UID/SID 从真实密码流程取得。授权登记仍使用另一个受限登录；旧 `r3-verifier.mjs` 是证书登录实现，托管直连所支持的独立认证方式需要接线和审查。
- ingress 文件含 `ca`、`cert`、`key`、`trustedFingerprint`（客户端指纹）和 `socketPath`。客户端文件含 `ca`、`cert`、`key`、`aliceToken`、`bobToken`。两份文件均为 0600，密钥、JWT 与密码放在 Git 之外。客户端与现场观察进程使用不同凭据。
- 真实入口的前提是业务 Grant 已由现有 R3 密码登录、签署、登记、消费链签发，两个站点由各自普通用户通过 `create_site` 建立。已合成的测试入口无法替代该环节。当前尚待完成和验证托管 registrar 认证、密码登录签署接线、M5 受控激活和 fixture 授权。管理员仅可准备两个合成 Auth 用户、登记代次和这两个用户安全状态的授权配置。

```sh
node scripts/s36-hosted/ingress.mjs "$TEST_CONFIG" "$INGRESS_TLS_FILE"
node scripts/s36-hosted/acceptance.mjs "$TEST_CONFIG" "$USER_SESSIONS_TLS_FILE" "$NEW_LOCAL_JOURNAL"
```

测试先确认匿名请求被真实 ingress 拒绝，然后用真实 Session 检查 Alice/Bob 均有自己站点的读取资格。对 Bob→Alice 和 Alice→Bob 分别要求读取、写入明确拒绝，再由 Alice 对初始文案保存一次固定合成内容，核对 revision 1、Bob 不变、原请求 ID 的事务回执。以 `psql -X -v ON_ERROR_STOP=1` 单独运行 `supabase/candidates/s36-hosted/observe-first-save.sql`，传入 `alice`、`alice_sid`、`alice_site`、`bob_site`、`request_id` 五个变量。须读回真实结果、revision、actor/Session、同一操作的审计关联和 unpublished 指针。应用成功仍显示 `APPLICATION_CHECKS_PASS_AUDIT_PENDING`，独立审计通过才合并判定。此批跨站指跨站点 ID；浏览器 CSRF 和 UI 另测。

## 下一次执行范围

1. 确认全新 `example-cv-s3-acceptance`、Singapore `ap-southeast-1`、PG17、实际组织/项目 ref 和费用。优先使用独立测试组织的可用 Free 配额（预期 USD 0）。当前可见的 Example CV 组织是 Free，可见的两个项目均被排除。是否有可用免费名额须由创建界面或已授权的报价确认。另建独立 Pro 组织单个 Micro 的标价约 USD 25/月，须由明确报价及批准决定。
2. 对选定新项目只读核对版本、空 catalog、当前 Auth 列权限、角色委托、业务 schema 及默认 ACL；另核查私有 PostgREST、两个登录身份、登记 TLS 方案及正式运行材料。只读能力失败即停。
3. 写入边界为该项目的 M1–M7、01 和独立审阅后的闭态迁移。审阅并单独确定 M5 激活变更，只允许此目标、专用角色及代次。绑定真实 Session、保持 Grant 默认拒绝、保持 publish/unpublish、public read 和 outbox 关闭。夹具限两个确认测试账户、两站、固定默认文案及一条 Alice 合成保存请求。禁止真实个人数据、Storage 及生产同步。
4. 按入口执行负例和 Alice 保存，独立读回。目标/权限漂移、负例没有明确拒绝、版本/审计不一致、首次写入后回执丢失立即停止。保留原 request ID 和本地 journal，按同键只读对账。收尾关本地监听并按批准的保存策略处理测试会话和凭据；资源处置另行确认。
5. 首轮真实通过后再扩展并发 CAS、同键幂等重放、故障回滚、UNKNOWN、会话/Grant 撤销、发布与撤回，随后评估 02 和 S3.5。托管证据可验证业务边界与事务。它无法证明旧 REF 的固定版本、SID、4 GiB 路径、ENOSPC、Watchdog、UTM 启动或历史 A07/A50 边界。
