# S3.6 托管 Outbox 后续批次

原覆盖索引 R20–R24。只适用于 `vellypyadcxkvqftsbrg`。此前真实 PostgreSQL 回滚探针证明了 SQL 分支行为。跨事务持久生命周期和隔离投递仍为 NOT_RUN。本清单及 `--plan-only` 入口只生成锁定的事件和 SQL 输入，真实执行另批授权。

## 准入和最小身份

1. 从已关闭发布 ACL 的独立读回生成事件清单。运行 `node scripts/s36-hosted/outbox-batch-plan.mjs --plan-only <final-business.json> <fixture.json> <私有输出目录绝对路径>`，入口独占写入清单正本和摘要绑定，派发前由未来执行器核对审查过的 SHA-256。每一步的 SQL、已冻结的 owner/token、generation、分支及数量上限均在正本中。清单应只有 Alice 的 revision 1–5 五条实际 pending 事件，均零 attempt、零 lease generation，且每条与持久发布历史、operation ID 一致。执行前重新独立读回并比较，同一事件状态或当前指针漂移即停止。
2. 现有 `ecv_s36_outbox_worker` 保持 NOLOGIN、NOINHERIT、NOBYPASSRLS，无其他业务权限。下一批若获准，使用单个全新短期 worker login；仅赋予 `SET ROLE ecv_s36_outbox_worker`，无 INHERIT 或 ADMIN。先读回登录/成员路径、LOGIN 到期、现有函数 Owner、列级 ACL、FORCE RLS 和零其他连接。禁止给现有 app/registrar/API login 新增成员路径。固定同一 TLS 校验过的 Session Pooler，最多两个专用 worker 连接。每次短事务以 `SET LOCAL ROLE` 运行一个白名单函数，验证 session_user/current_user，独立提交后下一步才能派发。HTTP 发送期间无数据库事务。未来操作端须在连接上实现此边界。执行器在派发前和每个事件后另起独立会话核对当前指针，current 回执也须匹配冻结指针。按清单顺序单次消费，每步均须有回执，唯一并发组只含 revision 1 的两次 claim，不能任意改 token 或跳步。
3. 仅开启本项目 `outbox_enabled`，执行前确认 `public_read_enabled=false`、发布 ACL 已关闭、无其他 worker。监听只绑定本机 HTTPS loopback，沿用验过的测试 TLS/客户端验证方式，禁重定向、代理和外部网络。发送固定四字段 event/site/publication revision/event type，以 event UUID 作为幂等键。接收端写独占文件并 fsync 后才应答。相同键只能返回同一条接收回执，固定负例不能放行其他事件 ID。脱敏回执只含事件元数据。当前交付摘要准入、接收去重原语及只绑定 loopback 的 mTLS 接收器工厂。未来执行批次须用获批摘要和客户端证书指纹实例化并启动监听，使用现有私有 mTLS 客户端，校验无代理和无重定向，再验通信。

## 固定动作表

基础批仅用五条固定事件、最多 30 次 worker 函数调用、1 次实际 loopback HTTP 发送，另预留 8 次独立只读核对及鉴权读回。常规 lease 为 5 秒，过期专用 lease 为 1.5 秒，逾期依据数据库读回的 lease_until 和 server clock。连接/语句/单次发送期限分别不超过 8/8/2 秒，总窗口 180 秒，另留 60 秒关闭和只读回查。各数据库操作按下表分开提交，禁止把整批合并成一个回滚事务。

| 事件 | 具体动作和独立证据 | 函数上限 / 发送 |
| --- | --- | --- |
| revision 1 | 两连接用不同 owner/token 在 generation 0 同时 claim，一次成功、另一次冲突。独立 read 一条 lease，wrong-token finish（必须失败），正确 token finish superseded，再次 claim 不领取。 | 6 / 0 |
| revision 2 | claim 后不 start，自然到期后 claim(false) 持久化 failed。显式 retry=true 到 attempt 2，重复到期并持久化 failed，再显式重试到 3。到期后再次 retry 只能标 failed 并拒绝第四次领取。独立 read 验 cap、三代 token 与零 dispatch。 | 7 / 0 |
| revision 3 | 固定的旧事件 SQL 故障注入。claim、start 后在网络派发前中止执行，等 lease 到期。只用原 UUID claim(false) 确认 UNKNOWN。旧 token 的迟到 finish 和再次 claim 均不能推进。独立 read 确认终态。此用例无 sender。 | 6 / 0 |
| revision 4 | 正常 worker claim，读取当前 revision 5，finish superseded，独立 read 证明旧发布从未被发送。 | 4 / 0 |
| revision 5 | claim，读永久当前指针为未发布且 revision 匹配，start 后发送一次真实 loopback invalidation。接收端持久化，应答后一次 finish delivered。丢弃客户端的 finish 成功回执，再用原 event ID 独立 read。重复 claim 不再投递，最终 read 与接收唯一回执对账。 | 7 / 1 |

R24 的真实发送应答丢失需要第二条可投递的当前事件。若一批内也批准该场景，先完成 revision 5 的真实成功用例，再让 Alice 用旧快照显式发布一次，前置草稿/发布版本为 5/5，生成 revision 6；按新事件独立读回锁定 UUID 后才接入接收端。对 revision 6 唯一发送一次，接收端 fsync 后有意关闭连接，使用同一 event/lease 对账并持久化 UNKNOWN，禁止在收到迟到应答后重发。最后用已锁定的唯一请求键撤回到 revision 7，保留该新 pending。预算增量为 2 次合成发布状态写入、7 次 worker 调用及 1 次实际 loopback 发送。发布写入仅限临时 ACL 和既有 Alice 普通身份。若需新 R3 Grant，继续使用 Alice 当前 epoch 0；新代次只授予 Alice，未来启动夹具应核对 Bob 现存 epoch 1 并保持原值。第二场景的应用边界、revision 6 接收 UUID 与新请求 ID 必须在获批后绑定，当前基础清单的 SQL 函数和接收端只放行已读回的五条事件。

## 收尾与证据

每个已派发阶段分别持久记录 event/owner/token/generation、数据库提交/拒绝、接收端唯一性和时间。已知失败仅能在表中明示的原 event 上重试。发送或提交不明立即停下一步，原 event ID 独立对账，禁止替换 token、事件 ID 或更换连接补发。超过期限、原生角色或事件范围异常、未知连接、接收证据不匹配时停止后续派发。两条回执轨迹分别为数据库生命周期和 loopback 应答；探针、持久数据库状态、实际网络传输各自单独判定。

关闭 outbox gate、停止发送器及监听器、确认测试 worker 会话归零，撤销新登录的临时角色路径并按批准的归属清理登录。独立核对 02 目录与权限、发布 ACL、未发布指针、全部原事件及终态。保持旧 SQL 回滚探针和所有 STOP/UNKNOWN。外部生产投递和公开网站部署均在本批之外。
