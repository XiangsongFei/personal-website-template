### 部署角色与提交条件

- PostgreSQL 17 为非超级用户创建的新角色自动写入 bootstrap 成员记录。
  每个内部角色只允许一条指向 `postgres` 的记录，且 ADMIN=true、SET=false、
  INHERIT=false。授权者必须是 PostgreSQL 固定 bootstrap OID 10，且在 Supabase
  目录中对应 `supabase_admin` 超级用户。此名称只用于核对目录元数据。
- M1 在事务内关闭可选的 `createrole_self_grant`。M1/M2 各自显式以
  `postgres` 为授权者取得两条临时 SET 记录。Owner 记录也允许 INHERIT，
  使 `postgres` 可同时使用业务 Schema 权限和既有 Auth FK 权限，并在对象
  转移后完成 Owner DDL。integrity 记录只允许 SET。各角色的全局函数默认 ACL
  在切换到该角色后修改，随后恢复会话角色。
- M2 取得临时权限前检查已提交的角色目录。两份 Migration 分别按授权者撤销
  本事务的临时成员记录，并在 COMMIT 前检查实际目录中的记录数、角色属性、
  授权者及选项。任何额外记录、非超级用户的传递成员路径、API 角色的成员
  路径，或 `postgres` 仍具有效 SET/USAGE，都会中止事务。
- `postgres` 的 bootstrap ADMIN 允许将来再次自行授权。它属于部署管理边界，
  已有 BYPASSRLS 属性保持原样。普通请求只走已审核的 JWT/API 身份链；
  不得使用部署会话、其代理角色或 `service_role` 代替用户。

[PostgreSQL 17 角色属性](https://www.postgresql.org/docs/17/role-attributes.html) ·
[Supabase bootstrap 成员关系说明](https://supabase.com/kb/troubleshooting/cant-revoke-a-role-membership-granted-by-supabase_admin-d08922)

## 安全封闭策略

- site_data/site_private 不应加入 Data API exposure；site_api 当前为空、也不应曝光。
  Migration 不修改 PostgREST 配置；实际 exposure 仍需下一轮独立只读核查。
- 15 张表逐一 ENABLE/FORCE RLS；普通角色、PUBLIC、service_role、authenticator
  都明确撤销表和 Schema 权限；没有 authenticated/anon 业务策略或 RPC。
- BYPASSRLS 不等于拥有表 ACL；service_role 也不在本基础中获得表权限。
  超级用户与维护者可绕过/改写对象，不属于普通请求安全证明。
- ecv_s3_owner：NOLOGIN/NOINHERIT/NOSUPERUSER/NOBYPASSRLS，持有 Schema/表及
  三个 invoker 触发器函数；仅保留上述部署管理员 bootstrap ADMIN 例外，
  无公开调用入口。
- ecv_s3_integrity：同样 NOLOGIN/NOINHERIT/NOBYPASSRLS；仅有 site_data/site_private
  USAGE 和 sites/members/publications SELECT。三条仅面向此角色的 RLS SELECT
  policy 允许延迟检查，无写入、grant、Auth/session 读取权。
- 唯一 SECURITY DEFINER 是 trigger-returning `assert_site_integrity()`，Owner 为
  integrity 角色；固定空 search_path、显式限定表名，无动态 SQL、无 actor 参数。
  转移函数所有者所需临时 CREATE 在同事务中立即撤回。没有授权普通用户 EXECUTE。
- 其他三个函数 SECURITY INVOKER，Owner 为 ecv_s3_owner；四个函数均固定空
  search_path，逐个撤销 PUBLIC/外部角色 EXECUTE；仅供触发器，不是业务授权 helper。
- 默认 ACL：为实际 Migration 创建者在新 Schema 撤销表/序列/函数外部默认授权；
  为两个新内部角色全局撤销默认 PUBLIC EXECUTE。PostgreSQL 每 Schema 默认撤销
  不能抵消创建者的全局 PUBLIC EXECUTE，故现有对象还逐一显式 REVOKE。
  不修改迁移者跨 Schema 的全局默认 ACL，避免影响旧系统。
- 后续创建对象必须重新检查实际 creator 的全局/Schema 默认 ACL，且在同 Migration
  显式封闭后才 COMMIT；不能把本轮默认 ACL 当所有未来角色均安全的证明。

## 建站幂等：结构已准备，业务命令 BLOCKED

- request_id 是客户端生成并重试沿用的 UUID，只标识请求，不授予身份。
- site_id 由未来数据库事务 `INSERT sites ... RETURNING id` 的随机 UUID 产生；
  不由 email/slug 推导，不信任客户端 site_id 建立所有权。
- 站点不存在时不插入孤儿 operation、不令 site_id 可空、不提前提交预留。
  未来先锁可信 UID 的 user_security_state；在配额检查前按 actor/operation/request
  查原回执；新请求才建 site，随后同事务插入回执，NOT NULL site FK 始终完整。
- 保留 S3.2 `(site_id,actor,operation,request_id)` UNIQUE，增加仅 create_site 的
  `(actor,operation,request_id)` 部分唯一索引，支持不知道 site_id 的原请求查找。
- 基础仅允许 create_site/succeeded 最终回执；结果必须为对象且 site_id 字符串
  对应本站；同站 FK 绑定权威 Owner。pending 是未提交竞争/外部状态，不伪造已提交结果。
- digest 为规范化完整载荷的 SHA-256；表只检查格式并冻结回执，不能证明摘要正确。
  未来命令必须可信计算并比较：同键同摘要返回原结果，同键异摘要 409，不 UPSERT 覆盖。
- 回执/基线/成功审计不可 UPDATE/DELETE；expires_at 不触发清理或释放 request key。
  7 天仅是 fixture 值，非获批生产保留参数。不得因到期自动以新请求重建网站。
- 成功提交丢响应：未来 read_create_operation(request_id,digest) 从真实 JWT 获取
  actor，先验证业务资格及本站归属，再返回最小结果；不接受 actor 参数、不按 email 查。
  查不到保留 UNKNOWN，同 request 重试；未提交事务仍可能在途。
- 同账号并发最终由 owner 全局 UNIQUE 拦截；不同账号抢域名由 hostname UNIQUE
  拦截；未来命令仍须统一安全状态→site→operation 锁序和异常分类。
- 本轮不实现该查询函数、create_site 或业务资格 policy。缺少 proof 验签能力时
  这些入口 BLOCKED；不以 service_role、客户端 UID 或 GUC 代替可信授权。

## Owner、归属及初始状态

- sites.owner_auth_user_id 权威且全局唯一；软删除不释放名额；ID/Owner 更新被拒绝。
- 首版 members 只接受 active owner；PK(site,UID)，部分唯一保证至多一条；
  (site,UID) 延迟 FK 对应 (sites.id,sites.owner)，确保 UID 一致。
- sites/members/publications 三侧延迟约束触发器在事务结束检查存续 site 恰有
  对应 Owner 镜像和 publication；缺少镜像或 publication 不可提交。
- 没有业务 DML 权限；没有成员转让/团队/修复入口；不要把 NOLOGIN/NOINHERIT
  单独当作 SET ROLE 安全，须同时核查精确成员记录及普通角色传递路径。
- site 子表均有 FK；翻译用 (site,parent) 与 (site,locale)；revision/audit 使用
  (site,operation)；归属/父级身份更新拒绝。无自动 CASCADE 删除生产数据。
- publication 在同建站事务创建；仅允许 unpublished、snapshot_id=NULL、revision=0；
  更新和删除均拒绝。即使零版本也不能删行重建。S3.6 必须同次 Migration 补齐
  快照/同站 FK/outbox/完整状态机，再替换本闭合 CHECK/触发器及开放精确发布权限。
- site/section/draft revision 当期锁定 0，避免没有历史机制的裸内容写入被当成保存。
  Introduction 表仅为基础形状和双语归属样例；不提供编辑/聚合保存入口。
- Owner/publication 恰好存在有数据库延迟检查；locales/settings/domain/基线/审计
  的完整初始化仍必须由未来建站事务执行。本轮 fixture 示范完整事务形状，不声称
  任意超级用户 INSERT 都会自动补全，也没有注册/登录建站触发器。

## Business Grant 依赖与未决

仅准备 UID/安全 epoch/session/purpose/时效/撤销、proof action/project/digest/key ID
等基础字段。不存 Token/密码/签名密钥；security state 默认 disabled + hold。
epoch 是快照，不 FK 绑定“当前 epoch 值”，否则递增会被旧 grant 阻塞。
不对 auth.sessions 建生命周期 FK，不查询/公开它；真实会话有效性检查另批。
proof 一次消费、签名算法/可信 signer、grant 不复活/续期、撤销联动/S2 集成全部 BLOCKED。
本轮无 grant 发行角色、无签发函数、无密钥管理，不将基础 FK 宣称为业务授权。
